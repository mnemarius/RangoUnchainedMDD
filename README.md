# Rango Unchained: a game mode DSL

TDT4250 final project, group 6, autumn 2026.

*Rango Unchained* is a 2D arcade game (a Bubble Trouble clone built with libGDX in TDT4240). This
project introduces **game modes**, and makes the game into a software product line with multiple editions with different game mode configuration. An *edition* of the game is
described in a small textual language. The DSL tools validate the description and generate the game
modes into the game: the rules as Java code, the arenas as level resources, and the product name into
the menus, the desktop launcher and the Android manifest.

```
edition Arcade "Rango Unchained: Arcade"

enemy Mine {
	sprite "Enemy/Bomb.png"
	points 30
	on pop: split into 4 Weed
	on contact: damage 2
}

difficulty hard {
	enemy.speed * 1.3
	player.health * 0.5
	drop.chance * 0.5
}

mode TimeAttack "Time Attack" {
	player Sprinter
	speed bonus up to 2 times over 60 s
	arena {
		background "Desert"
		jumppad Launcher at (25%, 0%) launch 10 affects player
	}
	waves looping escalate by 1 {
		wave { 2 * Tumbleweed size 3 at (50%, 80%) }
	}
	drops {
		Tumbleweed 10% { Heart }
		Weed 15% { Heart weight 2, Thorns }
		Mine 50% { Rush weight 3, Heart }
	}
	win when score reaches 1500
	lose when time reaches 90 s or health depleted
}
```

## Quick start

Requires JDK 21 or newer. Run these in the repository root.

macOS and Linux:

```sh
./mvnw package -Pgame "-Dedition=arcade"   # or classic, hardcore
cd rango-game
./gradlew lwjgl3:run
cd ..
```

Windows (Command Prompt or PowerShell):

```bat
.\mvnw package -Pgame "-Dedition=arcade"
cd rango-game
.\gradlew lwjgl3:run
cd ..
```

The first run takes a few minutes.

### Using the generator

Copy `no.ntnu.tdt4250.rango.gamemode.examples/arcade.rango` to `my-edition.rango` in the repository
root, edit it, and run the Quick start with `"-Dmodel=my-edition.rango"` instead of `"-Dedition=arcade"`.
A model with errors is not generated; the errors are printed.

`-Pgame` runs `no.ntnu.tdt4250.rango.gamemode.dsl.generator.Main <model> <game folder>` (the folder is
`rango-game` unless you set `"-Dgame.folder=<path>"`). [Generation](#generation-from-model-to-game)
lists the files it writes.

### In Eclipse

1. Import every project except `rango-game` into Eclipse 2026-06 with Xtext and OCL (*File > Import >
   Existing Projects into Workspace*).
2. Run `no.ntnu.tdt4250.rango.gamemode.dsl.ui` as an *Eclipse Application*.
3. In the new Eclipse, import `no.ntnu.tdt4250.rango.gamemode.examples` and open a `.rango` file.
4. Right-click it and choose **Generate Game Modes into Game...**, then select `rango-game`.

To install only the editor, use the update site in
`no.ntnu.tdt4250.rango.gamemode.repository/target/repository/`.

## The variability aspect

In the original game, we only had the current campaign where you chose which JSON level to load. How enemies split, what they do to
the player, what drops, and when a round is won or lost were all hard-coded. This project models
exactly that. Following the feedback on our draft, the building blocks are *library elements with
behaviour*, not enumerations of the enemies we happen to have. An enemy type is defined by its tuning, by
the split rule it owns, and by the effects it has on contact. "Cactus", "Bomb" or "Bubble" are just
instances. Everything in the model is implemented in the game.

## The metamodel

![Class diagram of the metamodel](docs/metamodel.png)

An **Edition** (the root, one product) contains reusable building blocks and the game modes made from
them:

- **EnemyType**: sprite, scale, bounce, speed and points. It *contains* one **SplitRule** and one or
  more **PlayerEffect**s (what it does on contact).
  - SplitRule is either **Vanish** or **Split** (fragments, launch speed, an optional *reference* to
    the fragment type). The number of fragments decides the pattern: fragments leave 45° apart,
    centred on straight up, so two fan out like the original game and eight or more fly off all
    around. A Bomb that splits into Tumbleweeds is a cross-reference between enemy types.
- **PlayerEffect** is shared by enemy contacts and power-ups: **Damage**, **Heal**, and the abstract
  **TimedEffect** (duration), which is **Shield**, **SpeedChange** or **Poison** (damage over time).
- **PowerUp**: sprite and the effects it gives. **PlayerProfile**: health, max health, speed, tongue
  time, shot cooldown and grace time.
- **Edition** also *contains* the default **DropTable**s of its modes.
- **Edition** also *contains* its **Difficulty**s, which apply to every mode (see
  [Difficulty](#difficulty) below).
- **GameMode** *references* a player profile, and *contains* one or more **Level**s, an optional
  **SpeedBonus**, its own **DropTable**s, and its win and lose conditions. Its enemy types are not
  written down: they are derived from what its levels spawn.
  - A **Level** (optional title) *contains* an **Arena** and a **SpawnStrategy**. Each level is one
    round under the rules of the mode: the win and lose conditions are checked per level, and winning
    a level unlocks the next. A mode of one level can leave out the `level { ... }` block.
  - Each pop is worth the points of its enemy type. A **SpeedBonus** makes early pops worth up to
    `maxFactor` times as much, falling to plain points over `duration` seconds.
  - The **Arena** has a background, a player start, and **Obstacle**s: a **Block** (size) or a
    **Trigger**. A trigger is a **JumpPad** or a **Teleporter**, which references its target
    teleporter. Obstacles and spawns share the abstract **Positioned** (x, y in percent of the arena).
  - The **SpawnStrategy** is either a **FixedLayout** of **EnemySpawn**s, or a **WaveSchedule** of
    **Wave**s (delay, spawns), which can loop and grow by `escalation` enemies per round.
  - A **DropTable** belongs to one enemy type, which it *references*. It has a chance (the share of
    that enemy's pops that drop a power-up) and contains weighted **Drop**s, each of which
    references a power-up. If a mode has drop tables, they replace the edition's for that mode.
    Every enemy type that can appear in a mode, fragment types included, must have a drop table
    there (`everyEnemyDrops`). A Bomb that splits into Tumbleweeds rolls on the Bomb's table, and
    each Tumbleweed rolls on its own table when it is popped.
  - **EndCondition** is one of **Cleared**, **TimeReached**, **ScoreReached**, **EnemiesPopped**,
    **WavesSurvived**, **HealthDepleted** or **EnemiesAlive**. The same class can be a win or a lose
    condition. For example, TimeReached is "survive 60 s" as a win and a time limit as a loss. The
    role comes from the containing list (`winConditions`, `loseConditions`).

### Difficulty

An edition can have up to three **Difficulty**s, one per **DifficultyTier** (`EASY`, `MEDIUM`,
`HARD`). When an edition has any, the player chooses one after picking a mode, and it applies to
every level of that mode. Without difficulties, the modes are played exactly as modelled and the
game skips the choice (as in `hardcore.rango`).

A difficulty *contains* **Modifier**s. Each one multiplies one kind of modelled value, its
**ModifierTarget**, by a `factor`, in every mode of the edition. A value without a modifier keeps a
factor of 1, so an empty `difficulty medium { }` plays the modes as modelled.

| Target | What the factor multiplies |
| --- | --- |
| `enemy.speed` | The speed of every enemy type, in fixed layouts and in waves. |
| `enemy.points` | The points of every pop. |
| `player.health` | The starting and maximum health of the player profile, rounded, and never below one heart. |
| `player.speed` | The running speed of the player profile. |
| `drop.chance` | The chance of every drop table, capped at 100%. |
| `wave.delay` | The delay before every wave. |

Constraints: each difficulty changes each value at most once (`distinctTargets`), factors are
positive (`positiveFactor`), and each tier is defined at most once (`onePerTier`). The editor also
warns when a harder tier makes something easier than the tier below it.

### Derived features (Java, in `GamemodeDerivations`)

| Feature | Meaning |
| --- | --- |
| `EnemyType.producedTypes`, `Split.resultType` | What popping an enemy creates (the fragment type defaults to the enemy's own type). |
| `Split.spacing` | Degrees between neighbouring fragments: 45, or 360 over the count above eight. |
| `GameMode.enemyTypes` | The enemy types of a mode: those it spawns, and everything popping them can produce (recursively). |
| `EnemySpawn/Wave/SpawnStrategy/Level/GameMode.popsToClear` | Tongue hits needed to clear everything. Recursive over split rules and fragment types; -1 for looping waves. A mode sums its levels. |
| `Level/GameMode.maxScore` | Points for clearing everything. A mode sums its levels. |
| `Level.number` | Position of a level in its mode. |
| `GameMode.effectiveDrops` | The drop tables that apply in a mode: its own if it has any, otherwise the edition's. |
| `GameMode.powerUps` | The power-ups of the mode's effective drop tables. |
| `DropTable.totalWeight`, `Drop.share`, `Drop.probability` | How likely a power-up is when a pop drops something (`share`), and the chance that a single pop of the table's enemy type drops it (`probability`). |
| `Wave.number`, `EndCondition.win` | Position of a wave; the role of a condition. |

The generator, the hovers and the constraints all use these features.

### Constraints

Simple invariants are written in **OCL**, in the Ecore model, and evaluated by Eclipse OCL's
delegates. Standalone code registers the delegates through `GamemodeOCL.initialize()`. Examples:
`positiveScale`, `atMostSixteenFragments` (a split has 1 to 16 fragments), `intervalWithinDuration`
(poison ticks within its duration), `insideArena`, `healthWithinMaximum`, `escalationNeedsLoop`,
`chanceIsPercentage` (a drop chance is above 0 and at most 100), `distinctPowerUps`
(`entries->isUnique(powerUp)`), `notToItself` (teleporters), `bonusAboveOne` (a speed bonus is worth more than plain points),
`distinctTargets` (a difficulty modifies each value at most once), `positiveFactor`.

Rules that span several objects are in **Java** (`GamemodeConstraints`). They have stable diagnostic
codes:

| Constraint | Rule |
| --- | --- |
| `nameUniqueAmongSiblings` | No two elements of a list share a name. |
| `distinctEffectKinds` | An enemy type or power-up has at most one effect of each kind. |
| `noSimultaneousOutcome` | In no level can a round be won and lost by the same event (survive 60 s vs. a 60 s time limit), nor start already lost (`EnemiesAlive` at or below the starting number of enemies). |
| `winnable` | Every win condition can be met in every level: no "all enemies cleared" with looping waves, no "8 waves survived" with 5 non-looping waves, no more pops or points than the mode can give. |
| `endsSomehow` | A mode without win conditions must loop its waves, and a mode of several levels needs a win condition to move on. |
| `healthDepletedWhenHarmful` | If anything can hurt the player, the mode is lost when health runs out. |
| `everyEnemyDrops` | Every enemy type that can appear in a mode has a drop table there (the mode's own, or the edition's), so popping any enemy has a chance to drop a power-up. |
| `oneTablePerEnemy` | A list of drop tables (of a mode or of the edition) has at most one table per enemy type. |
| `fitsRole` | Health depleted and enemies alive can only lose a round; the other conditions can only win it. |
| `targetInSameArena` | A teleporter leads to a teleporter of the same arena. |
| `onePerTier` | An edition defines each difficulty tier at most once. |

## Concrete syntax and editor

The grammar (`RangoMode.xtext`) imports the hand-made metamodel instead of inferring one, so all
constraints and derived features apply to models written in the editor. It is customized to read like
a description of the game. Tuning can be written in any order (unordered groups). The syntax has
units (`8 s`, `25%`), positions (`at (30%, 45%)`), counts (`2 * Tumbleweed size 3`), readable end
conditions (`win when 20 enemies popped or all enemies cleared`), and difficulties written as the
factors they apply (`difficulty hard { enemy.speed * 1.3  player.health * 0.5 }`).

The editor adds:

- **Validation**: the OCL and Java constraints of the metamodel, plus warnings for unused building
  blocks, sprite paths that are not images, duplicate titles, and drop tables for enemies that never
  appear where the table applies, a harder difficulty that makes something easier than the tier
  below it (such as slower enemies on hard than on medium), and a note on endless modes.
- **Scoping**: a teleporter can only target another teleporter of its own arena.
- **Quick fixes**: make a mode end (win when cleared, or loop the waves), add "lose when health depleted", move a condition to the other
  list, add drop tables for the enemies without one, remove an unused element or a drop table without
  effect, fix sprite and background paths.
- **Hovers** that show the derived facts: the enemy types of a mode, pops to clear, maximum score, drop
  probabilities, what an enemy breaks into, shots per second, and what each difficulty multiplies in
  which modes.
- **Outline** with icons and summaries ("Mine: splits into 4 Weed", "win when score reaches 1500",
  "enemy.speed ×1.3").
- **Content assist** for the images the game ships and for enemy sizes, and **templates** for enemy
  types, power-ups, players, difficulties, modes, levels, waves, teleporter pairs and drop tables.
- **Formatter** (*Source > Format*), and the **Generate Game Modes into Game...** command.

## Generation: from model to game

`RangoModeGenerator` (Xtend) writes into the game's own folder layout:

| Generated file | Content |
| --- | --- |
| `core/src/generated/java/.../Modes/Generated/<Mode>Mode.java` | One class per mode, extending the runtime's `GameModeDefinition`. Split rules become `split` calls (with the derived spacing), effects become calls on the player, each enemy type's drop table becomes a chance roll and a weighted pick inside that enemy's case of `onEnemyPopped` (commented with the derived shares and probabilities), fixed layouts become spawn calls at the start of a level and waves become spawn schedules with escalation, triggers become arena-building calls, and end conditions become the boolean expressions of `isWon` and `isLost`. |
| `assets/modes/<Mode>-<n>.json` | The arena of each level in the game's existing level format: background, player, walls, floor and roof, and blocks. Positions are relative to the arena. |
| `core/src/generated/java/.../Modes/Generated/GeneratedEdition.java` | The product name, the modes in menu order, and the difficulties from the easiest tier to the hardest, each with the factors of its modifiers (`new Difficulty("hard", "Hard").with(Difficulty.ENEMY_SPEED, 1.3f)`). Read by the main menu, the difficulty menu and the desktop launcher's window title. |
| `android/res/values/edition.xml` | The product name for the Android launcher label. |

Earlier generated files are removed first, so a mode deleted from the model disappears from the game.

### The game runtime (hand-written, `rango-game/core/.../Modes/`)

The generated classes plug into a small runtime added to the game:

- `GameModeDefinition` is the contract. Level-specific parts (arena, triggers, waves) take the level.
- `ModeSession` runs a round, that is one level: the wave scheduler, timed effects (shield, speed, poison), grace time,
  teleports, and the statistics the end conditions check.
- `ModeContactRules` replaces the original fixed contact strategies when a mode is played.
- `ModeProgress` remembers the unlocked levels of each mode across restarts.
- `Difficulty` holds the factors of one tier (1 for a value it does not change).
  `DifficultyAdjustedMode` wraps a generated mode and multiplies its enemy speeds, player profile,
  wave delays, points and drop chances by them. The rest of the game sees an ordinary
  `GameModeDefinition`, so the generated mode classes do not depend on difficulties.

Hooks in the existing code are kept small:

- Factories read enemy kinds, sprites, player speed, tongue time and cooldown from the mode.
- The physics system applies the bounce of each enemy type and, on each floor bounce, caps its horizontal speed at
  the type's speed.
- The level loader accepts arena-relative positions. When a level starts, the level controller lets the mode build
  its triggers and place the enemies of a fixed layout through the same spawner as waves, so both are spread out the
  same way and move at their type's speed, which the difficulty's `enemy.speed` factor scales.
- The main menu lists the modes of the edition, each with its description, and the tutorial. If the edition has difficulties, a
  mode first opens the difficulty menu (`SelectDifficultyView`). A mode of several levels opens a
  level list (`SelectModeLevelView`), and the game over screen offers the next level once one is won.
- The player factory takes the player's health from the mode being played, so a difficulty can
  change it.

The tutorial and multiplayer are unchanged from the base game and not modelled.

## The three example editions

| Edition | Product | What it shows |
| --- | --- | --- |
| `classic.rango` | *Rango Unchained*, two modes | **Campaign**: the original game's five levels, each with its own arena (stone blocks) and layout, cleared one after the other to unlock the next. **Endless**: looping waves that grow every round, two ledges, a jump pad, teleporters for enemies, no win condition, and lost when overrun by 25 enemies. Four enemy types (a Bomb that *explodes into a ring of eight Tumbleweeds*, a Cactus that *poisons*) and three power-ups. Both modes use the *edition's drop tables*: the tougher the enemy, the likelier and better its drop. Three *difficulty tiers* apply to both modes, mostly through the calm between waves. |
| `arcade.rango` | *Rango Unchained: Arcade*, five modes | Two player profiles (fast and fragile vs. slow and tough). **Time Attack**: score with a speed bonus under a time limit. **Pop Frenzy**: harmless Bubbles that *vanish* but slow you down, low gravity, a trap power-up. **Survivor**: survive 60 s in an arena split by a pillar, crossing it through player teleporters. **Wave Rush**: five waves to survive under higher gravity. **Minefield**: clear the mines in heavy gravity within 45 s. Every mode has *its own drop tables* (no edition defaults), so the same Mine drops a Rush in Time Attack but a trap in Minefield. |
| `hardcore.rango` | *Rango Unchained: Hardcore*, one mode | **Gauntlet**: one heart and no healing (the only power-up is a short shield), against fast enemies that split into more of themselves: a Bomb bursts into four Armadillos, an Armadillo into three, a Cactus poisons. The edition has *no difficulty tiers*, so its mode plays exactly as modelled. |

The tests check that all three are valid and that together they use every concrete class, every
feature and every enumeration literal of the metamodel.

## Tests

`./mvnw verify` runs:

- `no.ntnu.tdt4250.rango.gamemode.tests`: every derived feature, every OCL invariant of every class
  (also where several classes share a name, such as `positiveCount`), and every Java constraint. Each
  test breaks one rule of a valid fixture and checks that exactly that rule fires. The one exception
  is a lose condition of 0 enemies alive, which also breaks `noSimultaneousOutcome`: the round would
  be lost the moment it starts.
- `no.ntnu.tdt4250.rango.gamemode.dsl.tests`: the examples (validity and metamodel coverage),
  constraint and DSL errors in the editor with their issue codes, scoping of teleporters, the
  generated files and their content, and the formatter.

## Building blocks of the build

- The target platform is Eclipse 2026-06: EMF, Eclipse OCL, Xtext 2.43 and JUnit 6.
- The language module runs the MWE2 workflow in `generate-sources`, which regenerates `src-gen/`
  of `.dsl`, `.ide`, `.ui` and `.tests` from the grammar. It then compiles the Xtend generator with
  `xtend-maven-plugin`.
- The game is built by its own Gradle build. The Android module is only included when an Android
  SDK is configured.
